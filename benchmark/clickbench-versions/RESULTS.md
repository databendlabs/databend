# ClickBench 本地版本对比（构建参数对齐，默认配置）

日期：2026-11-21。比较 ClickBench 现用的 Databend v0.9.53、v1.2.955、v1.2.967 官方包，以及按发布 CI 参数本地构建的 v1.2.967 和 main + #21138 + #21144。所有版本都用默认配置。

2026-11-23 补充了同格式对比（`probes/`），据此修正了第 4、8 点：之前把逐题回退归因于代码，实际上主要是存储格式不同。

所有输入、脚本、原始数据和复盘步骤都在本目录，说明见 `README.md`。两个本地构建的二进制没有提交，只记录了 sha256。本文的"环境"及之后各节由 `report.py` 生成。

## 结论

1. **构建参数已对齐。** 本地按发布 CI 参数构建的 `official-967` 和官方 v1.2.967 包相比，热跑几何平均 1.029，热跑总和 23.61 s 对 23.43 s，没有一题有稳定差异。`.text` 大小也一致。所以本地构建可以和官方包直接比。
2. **official-main-prs 是五个版本里最快的。** 它的冷跑总和 30.61 s、热跑总和 22.47 s 都是最低。和同参数构建的 967 相比：
   - 热跑总和少 4.8%（23.61 → 22.47 s），冷跑总和少 2.5%，热跑几何平均 0.969；
   - 逐题峰值 RSS 的几何平均少 17%，Q32 的峰值从 16.6 GiB 降到 13.3 GiB；
   - 启动中位数从 1.53 s 降到 1.28 s；
   - 9 题稳定变快，没有一题稳定变慢。变快的题有：Q20 −27%（峰值 2.5 → 1.4 GiB）、Q10/Q11 −14%、Q24 −15%、Q26 −12%、Q03 −10%、Q21 −8%、Q31 −7%、Q27 −6%。
3. **和 ClickBench 现用的 v0.9.53 直接比，总和更快，逐题有 22 题更慢。** 热跑总和少 26%（30.36 → 22.47 s），热跑几何平均是 1.189；14 题稳定变快，22 题稳定变慢。变快的主要是重聚合：Q17 0.06×、Q32 0.42×、Q16 0.46×、Q28 0.46×、Q18 0.53×。
4. **这 22 题的回退主要来自存储格式，不是代码变慢。** 两边读的不是同一种格式：
   - v0.9.53 默认把表写成 Native 格式，执行计划里是 `SyncReadNativeDataSource`。
   - 1.x 只能写 Parquet：建 Native 表会报错 `native storage_format is no longer supported`。

   为了在同一种格式下比较，`probes/run_probes.py format` 在 v0.9.53 里另建了一份 Parquet 表（ClickBench 建表语句加 `STORAGE_FORMAT = 'parquet'`），然后在三种组合上各跑热跑（见下面"同格式对比"）。
   - 在同为 Parquet 时，测过的 17 题里有 11 题新版更快。字符串类全部变快：Q20 0.71×、Q22 0.77×、Q27 0.72×、Q10 0.73×、Q11 0.78×、Q24 0.15×、Q23 0.04×。
   - Q03 `AVG(UserID)` 之前看起来慢 2.3 倍，同格式下是 59.5 ms 对 62.0 ms（1.04×）。差距几乎全部来自格式。
   - 同格式下仍然更慢的只有几十毫秒的小查询：Q01 慢 9 ms（1.47×），Q02 慢 18 ms（1.57×），Q07 慢 14 ms（1.73×）。Q09（1.02×）、Q41（1.10×，相差 1.4 ms）在噪声范围内。
   - 这几道小查询多出来的时间，原因还没查清，已排除两个方向：
     - 打开 block meta 缓存（`block_meta_count`、`segment_block_metas_count`）后，耗时不变。
     - EXPLAIN ANALYZE 里每次热跑都显示 segment `decompress cost` 约 40 ms，但 Q41 整题只要 13 ms，所以这个数是多线程累加的，不能直接当作额外耗时。
   - 没有在同格式下测过的回退题是 Q00、Q29、Q36、Q38、Q42，都是几到几十毫秒的小查询。
5. **`length` 的语义变了，影响 Q27/Q28 的结果和耗时。** v0.9.53 的 `length` 按字节计数，1.x 按字符计数：`length('абв')` 在 v0.9.53 返回 6，在 1.x 返回 3。所以两边 Q27/Q28 的 AVG 值不同（Q27 首行 469.15 对 453.16）。ClickBench 的查询是按 ClickHouse 语义写的，ClickHouse 的 `length` 按字节计数。把 Q27 换成 `octet_length` 后，official-main-prs 从 1.06 s 降到 0.93 s，结果和 v0.9.53 一致。
6. **结果一致性。** 除了第 5 点，其他哈希差异都不是结果错误：
   - Q03 只是浮点格式不同（`-5.59e10` 对 `-55945124888.9`）。
   - Q17（`LIMIT` 没有 `ORDER BY`），以及 Q24、Q30–Q32、Q38–Q40（`ORDER BY … LIMIT` 有并列值），同一版本的 3 次运行之间结果就会变化。
7. **噪声。** 同一版本两轮之间，逐题热跑的偏差为 3.6–8.2%（几何平均）；热跑总和两轮相差不到 2%。
8. **对升级 ClickBench 的看法。**
   - 代码层面基本没有回退：同格式下大多数题更快，总和也最快。
   - 但 ClickBench 测的是默认表，新版只能用 Parquet，所以 22 道回退题在 ClickBench 上会保留，拉低逐题比值。要缩小这个差距，得让 Parquet 读路径在这些题上追上旧版 Native，而不是修某个回退。
   - Q01、Q02、Q07 这几道小查询每题多出的 10–20 ms 是真实存在的差距，值得单独查。

## 局限

- 用 `posix_fadvise` 逐出五个版本的文件来代替 `drop_caches`，不是整机清页缓存。
- 机器是 i9-12900KF，16 个逻辑核对应 8 个 P 核加超线程，调频策略是 `powersave`，内存 125 GiB。和 c6a.4xlarge 不同。
- 导入从 Parquet 分两步完成，和 ClickBench 的 TSV 流式导入不同，块的切分也可能不同（729–779 块）。
- 本地构建用 mold 链接，`.symtab/.strtab` 比官方包大。v1.2.967 及更早的版本会在启动时为 ELF 符号建索引，所以 `official-967` 的内存略高于官方包（峰值几何平均 1.061）。official-main-prs 已经移除了这个索引（#21129）。
- 测试开始前，用来等待主机空闲的一行脚本报错了。导入是在构建结束后立刻开始的，只有导入耗时可能受影响。第 0 轮第一格（v0.9.53 Q00）用的是旧阈值 3%，等满了 300 s；之后改为 10%。全部 430 格开始前的主机 CPU 占用都低于 9.9%。
